# 결함 관리 보고서

## 1. 보고서 개요

본 보고서는 QA 리드 엔지니어 관점에서 `docs/defect_report.md`에 결함 관리 기준서를 작성한 결과를 요약한다. 요청 범위는 결함 분류 체계, 결함 보고서 템플릿, 품질 메트릭 수집 계획, GitHub Issues 연동 워크플로우를 Markdown 문서로 정리하는 것이었다.

## 2. 작성 대상

- `docs/defect_report.md`

기존 결함 목록 문서인 `docs/defect_list.md`는 개별 결함 추적용으로 유지하고, 이번 문서는 결함을 어떤 기준으로 분류하고 운영할지 정의하는 상위 관리 문서로 작성했다.

## 3. 결함 분류 체계

결함 분류는 Severity 4단계와 ItemType 5종의 매트릭스로 구성했다.

| 분류 축 | 값 |
| --- | --- |
| Severity | Critical, Major, Minor, Info |
| ItemType | Requirement, Functional, Test, CodeQuality, BuildInfra |

Severity는 릴리스 차단 여부와 사용자 영향도를 기준으로 정의했다. ItemType은 요구사항, 제품 기능, 테스트, 코드 품질, 빌드/인프라 영역으로 나누어 결함 원인과 조치 담당 영역을 빠르게 구분할 수 있게 했다.

## 4. 결함 보고서 템플릿

결함 등록 템플릿에는 다음 항목을 포함했다.

- 상태, Severity, ItemType, 발견 단계
- 관련 요구사항, 관련 테스트, 대상 파일
- 재현 절차
- 기대 결과
- 실제 결과
- 원인 분석
- 수정 방안
- 검증 결과

이 템플릿은 `docs/defect_list.md`에 개별 결함을 추가할 때도 사용할 수 있고, GitHub Issue 본문으로도 그대로 사용할 수 있도록 Markdown 형식으로 작성했다.

## 5. 품질 메트릭 수집 계획

품질 메트릭은 현재 C++ 프로젝트에 바로 적용 가능한 항목과 향후 다른 언어 모듈이 추가될 때 사용할 항목을 함께 정리했다.

| 메트릭 | 목적 |
| --- | --- |
| 테스트 통과율 | 변경 후 기존 기능의 회귀 여부 확인 |
| 라인/브랜치 커버리지 | 제품 코드와 조건 분기 검증 수준 확인 |
| 단계별 결함 발견율 | 결함이 요구사항, 리뷰, 테스트, CI 중 어디에서 발견되는지 추적 |
| 결함 종료율 | Open 결함 처리 속도와 릴리스 잔여 리스크 확인 |
| 재오픈율 | 수정 품질과 회귀 위험 확인 |

C++은 `gcov/lcov`와 `gcovr`, Java는 JaCoCo, Python은 `pytest-cov` 기준 절차를 포함했다. 현재 프로젝트 기준 커버리지 목표는 `TVController.cpp` 라인 95% 이상, 브랜치 90% 이상으로 유지했다.

## 6. GitHub Issues 연동

선택 항목으로 GitHub Issues 연동 워크플로우를 작성했다. Issue 라벨은 Severity, ItemType, 발견 단계, 상태를 기준으로 구성하고, 브랜치와 PR은 결함 ID를 포함하는 방식으로 추적성을 확보하도록 했다.

권장 흐름은 다음과 같다.

1. Issue 등록
2. 결함 재현 테스트 또는 실패 조건 고정
3. 수정 브랜치 생성
4. 최소 변경으로 수정
5. 빌드, 테스트, 필요 시 커버리지 검증
6. PR 생성 시 `Fixes #이슈번호` 연결
7. CI 통과와 리뷰 승인 후 Issue 종료

## 8. 참고 사항

이번 작업은 문서 작성 작업이므로 제품 코드 동작은 변경하지 않았다. 빌드와 테스트는 신규 코드 변경이 없어 실행하지 않았으며, Markdown 문서 진단에서 오류가 없음을 확인했다.
